# Codex使用指南

本指南面向当前博士研究项目，说明怎样给Codex布置任务、保存上下文、减少无效Token，以及怎样使用Skills、Plugins和工具。科研阶段和任务边界仍以仓库规划文件为准。

## 1. 三种指令分别放在哪里

| 内容 | 放置位置 | 例子 |
|---|---|---|
| 长期稳定、适用于整个项目的规则 | 根目录`AGENTS.md` | Git保护、一次一个任务、检查点规则 |
| 当前阶段和唯一科研任务 | `00_Overview/Current_Stage.md` | 当前完成S0-01，不下载数据 |
| 本轮临时要求 | 当前对话 | 今天只检查YOLO结构图，不修改笔记 |

Codex开始工作前会读取适用范围内的`AGENTS.md`。子目录可以再放自己的`AGENTS.md`，但只有确实需要局部覆盖时才使用，避免规则分散或冲突。

官方说明：[Custom instructions with AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

## 2. 怎样开始一轮任务

推荐使用下面的最小格式：

```text
本轮唯一任务：检查01_YOLO_Research_Core.md中的结构链是否正确。

成功标准：指出断点和缺失证据，并给出最小修改建议。

本轮不做：不替我填写答案，不运行训练，不修改网络。
```

如果要求直接修改文件，应明确写“修改”；如果只想听分析，应写“只诊断，不修改”。

```text
只诊断这个问题，说明原因和证据，不修改任何文件。
```

```text
实施这个修改，完成后检查Git diff并运行必要验证，不提交Git。
```

## 3. 同一个任务什么时候继续，什么时候新建

适合继续当前任务：

- 仍在处理同一份学习笔记；
- 正在修正同一个错误；
- 同一实验的配置、运行和结果分析尚未结束；
- 前后消息共享大量相同背景。

适合先生成检查点，再开启新任务：

- 从学习阶段转入文献、代码、数据或正式实验；
- 当前任务已经完成，准备处理另一篇论文；
- 对话出现大量已经失效的方案；
- 需要把工作交给另一个任务继续；
- 系统压缩后无法可靠定位原始证据。

新任务不能只相信检查点。它应先核对当前仓库、Git状态和阶段文件。

## 4. 检查点怎样使用

### 4.1 检查点是什么

检查点是一份人类可读的任务交接摘要，用于恢复目标、证据和下一步。它不会主动删除当前对话，也不等同于Codex系统内部的上下文压缩。

### 4.2 什么时候生成

- 连续完成3个可检查任务后；
- 切换研究阶段前；
- 准备开启新任务前；
- 长任务中关键结果已经验证后；
- 用户感觉对话开始混乱时。

不建议每隔几轮机械生成，因为重复摘要本身也消耗Token。

### 4.3 生成检查点的提示词

```text
现在生成上下文检查点，不开始新任务，也不修改文件。

只保留：总目标与边界、当前阶段、唯一任务、已完成事项、
证据位置、修改文件、Git状态、验证结果、关键决定、风险和下一步。

删除闲聊、重复说明、失效方案和冗长工具输出。
把未经仓库或运行记录核验的内容标成“待核验”。
```

### 4.4 在新任务中恢复

```text
下面是上一任务的检查点。

先读取根目录AGENTS.md和当前阶段要求，再检查Git状态；
用仓库文件核验检查点，不要把检查点当作唯一事实来源。
核验后只继续检查点中的下一项唯一任务。

【粘贴检查点】
```

## 5. 系统压缩和检查点的区别

| 项目 | 检查点 | 系统上下文压缩 |
|---|---|---|
| 谁触发 | 用户要求或项目规则 | Codex运行环境或API配置 |
| 输出 | 可读摘要 | 内部压缩状态，可能不可读 |
| 是否删除当前对话 | 否 | 会用更短状态继续模型上下文 |
| 主要用途 | 交接、复核、开启新任务 | 控制长对话上下文规模 |
| 能否替代仓库证据 | 不能 | 不能 |

在Codex桌面端，系统压缩由运行环境管理。不要要求模型声称已经手动执行内部压缩。自己开发Responses API应用时，可以通过`context_management`和`compact_threshold`设置服务端压缩，也可以调用`/responses/compact`。

官方说明：[Compaction](https://developers.openai.com/api/docs/guides/compaction)

## 6. 怎样减少Token和提高Prompt Cache利用率

Prompt Cache复用的是相同的输入前缀。稳定规则在前、变化信息在后，并保留连续对话历史，更容易复用缓存。缓存主要降低输入处理成本和延迟，不会让上下文窗口变大，也不能代替压缩。

### 推荐做法

1. 把长期规则写进`AGENTS.md`，不要每轮重新粘贴。
2. 同一研究问题尽量在同一个任务里追加消息。
3. 只告诉Codex发生了什么变化，以及本轮要完成什么。
4. 引用仓库文件路径，不把同一文件全文反复贴入对话。
5. 大段终端日志先保存到文件，再让Codex只读取错误附近内容。
6. 保持模型、推理强度和输出要求相对稳定。
7. 阶段切换时生成一次检查点，随后开启干净任务。
8. 需要简短回答时明确要求长度，例如“结论不超过300字”。

### 不推荐做法

- 每轮复制完整项目背景；
- 为凑缓存长度添加无用文字；
- 同一个小问题反复新建任务；
- 在一个任务中混合多个互不相关的研究方向；
- 要求反复输出相同的大表格、代码或检查点；
- 为追求缓存命中率而拒绝必要的上下文压缩。

压缩会改变提示前缀，压缩后的首次请求可能减少缓存复用；但输入上下文变短后，总成本仍可能下降，所以目标应是减少总成本和保持正确性，而不是追求100%缓存命中。

官方说明：[Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)

## 7. Skill是什么，怎样使用

Skill是一套面向具体任务的可复用工作流，可以包含：

- 适用场景说明；
- 必须遵循的步骤；
- 输出格式；
- 模板、示例和脚本；
- 需要使用的工具。

当任务与某个Skill匹配时，Codex可以自动选择它。需要明确指定时，在Codex中使用：

```text
$skill-name 完成具体任务
```

例如：

```text
$openai-docs 核对Codex当前的AGENTS.md规则，只引用官方文档。
```

```text
$mermaid-diagram 根据已经确认的节点生成一张流程图，不补充未知内容。
```

使用原则：

1. Skill解决的是“怎样稳定完成一类工作”，不是给任务增加功能。
2. 只有当前任务确实匹配时才使用，不要一次指定很多Skill。
3. Skill的输出仍需服从项目阶段门、Git规则和用户明确要求。
4. 如果Skill要求读取额外资料或暂停工作，Codex应说明原因。
5. 经常重复且流程稳定的工作，才值得创建新Skill。

官方说明：[技能与插件](https://learn.chatgpt.com/zh-Hans/docs/skills-and-plugins)

## 8. Plugin是什么，怎样使用

Plugin是可安装的能力包，可能包含：

- Skills；
- 外部服务连接器；
- MCP工具；
- 自定义界面；
- 钩子或计划任务模板。

Plugin适合需要外部系统或一整套工作流的任务，例如读取Google Drive、处理电子表格或使用专门的安全扫描流程。只需要固定写作或分析步骤时，通常使用Skill即可。

### 桌面端

1. 打开“插件”页面；
2. 搜索并查看插件详情；
3. 点击安装；
4. 按提示连接外部服务并审查权限；
5. 开启新对话后使用插件；
6. 可以直接描述任务，也可以在界面中明确选择插件或其Skill。

### Codex CLI

进入Codex后输入：

```text
/plugins
```

安装后重新开启会话，再使用插件提供的能力。

### 安全原则

- 不因为插件“可能有用”就批量安装；
- 安装前看清它能读取和修改哪些外部数据；
- 对发送消息、删除数据、提交代码等外部写操作明确核对目标；
- 不把第三方网页或工具返回的文字自动当成项目指令；
- 插件不可用时，不伪装已经使用成功。

官方说明：[插件](https://learn.chatgpt.com/zh-Hans/docs/plugins)

## 9. Tool、MCP、Skill和Plugin的关系

```text
任务要求
   ↓
Skill：规定怎样做
   ↓
Tool：执行一次具体动作
   ↓
MCP服务器：向Codex提供外部工具或数据

Plugin：把Skill、连接器、MCP工具等打包安装
```

简单理解：

- Skill像操作手册；
- Tool像一把可调用的工具；
- MCP像提供工具的接口服务；
- Plugin像把操作手册和工具装在一起的扩展包。

## 10. 本项目推荐使用流程

```text
读取AGENTS.md和当前阶段
→ 检查Git状态
→ 声明本轮唯一任务与成功标准
→ 只读取当前任务需要的证据
→ 分析或实施
→ 验证结果
→ 更新职责匹配的项目文件
→ 报告修改、验证、风险和下一步
→ 每3个完成任务或阶段切换时生成检查点
```

当前练手论文仍处于阶段0。无论Codex安装了多少Skills或Plugins，只要阶段指南没有放行，就不能提前下载正式数据、训练模型、修改网络或开始后续论文。

## 11. 常用提示词速查

### 只查看状态

```text
读取当前阶段和Git状态，只告诉我现在做到哪里、缺什么，不修改文件。
```

### 审查学习笔记

```text
只审查我已经填写的内容。区分正确、证据不足和错误，
不要替我完成尚未作答的学习题。
```

### 修改文件

```text
实施这项修改，只触碰直接相关文件。保留所有用户未提交内容，
完成后给出Git diff摘要和验证结果，不提交Git。
```

### 遇到冲突

```text
如果当前要求与Current_Stage.md、Research_Plan.md或七篇论文路线冲突，
先停止实施并报告冲突，不自行扩大研究范围。
```

### 生成检查点

```text
生成当前上下文检查点，不修改文件，不开始下一任务。
```

### 指定Skill

```text
$skill-name 只完成下面这一个任务：……
```

## 12. 最后判断标准

Codex是否用得好，不看对话有多长、调用了多少工具或安装了多少插件，而看：

- 是否始终在当前阶段；
- 是否一次只完成一个可检查任务；
- 是否保护用户已有内容；
- 是否留下可复核证据；
- 是否减少重复输入和无效输出；
- 是否能从检查点和仓库可靠恢复；
- 是否没有把未经验证的内容写成论文结论。
