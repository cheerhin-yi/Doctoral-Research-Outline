# 像素–时延归一化表（Run I）

- **Run ID：** `P0-BENCH-I-PIXLAT-20261006-01`（2026-10-06 登记；PASS）
- **性质：** CPU-only；**无新推理、无训练**。只数“每张图送进网络的像素”，再与已冻结的逐图指标拼接。
- **脚本：** `P0_Benchmark/stage_i/run_i_pixlat.py`（原样 import 冻结的 `diagnose_bt1.axis_windows` 与 `stage_b/run_stage_b_timing.build_windows`；SAHI 切片直接调用已装 `sahi.slicing.get_slice_bboxes`，填充形状直接调用 `ultralytics.data.augment.LetterBox`）。环境 UAV_BT2：Python 3.10.22, numpy 2.2.6, sahi 0.11.32, ultralytics 8.4.90。
- **数据：** `04_timing/data/I_PIXLAT_summary.json`（含每种图像尺寸的逐协议几何 `geometry_by_size`）、`I_PIXLAT_table.csv`。
- **目的：** 把“提高分辨率（多处理像素）”的效应与“协议本身（怎么用这些像素）”的效应分开。

## 1. 几何规则（从冻结代码 / 已装库源码读出）

| 协议 | 送入网络的张量 | 来源 |
|---|---|---|
| F640 / F1280 | `model.predict(imgsz, rect=False)` → 正方形 letterbox，640² = 0.4096 Mpx / 1280² = 1.6384 Mpx | `stage_b/run_stage_b_timing.py::infer_full` |
| DensK1 | F640 + 1 个窗口；窗口裁剪贴到 640×640 画布（填 114），`imgsz 640, rect=False` → 共 2 × 0.4096 Mpx | `run_densk1` / `infer_patch` |
| UnifAll | F640 + `build_windows` 的全部窗口，每窗 0.4096 Mpx；`axis_windows(L) = sorted(set(range(0, max(1, L−640+1), 512)) ∪ {max(0, L−640)})`（640 窗、步长 512、末窗贴边） | `diagnose_bt1.axis_windows` |
| SAHI640 | `get_slice_bboxes(slice 640×640, overlap 0.25/0.25)`：步长 640−int(0.25·640)=480，越界切片贴边回退（不填充）；每片由 sahi 的 ultralytics 封装以 `predict` 默认 `rect=True`、ckpt `imgsz=640`（训练 `args.yaml`）推理 → stride-32 最小填充；**切片数 > 1 时**再加一次整图标准预测（`perform_standard_pred=True` 默认，同样 rect letterbox 到长边 640） | sahi 0.11.32 `predict.py` L304、`slicing.py::get_slice_bboxes`、`models/ultralytics.py::perform_inference` |

- 每图像素按真实图像尺寸逐图计算。VisDrone test-dev 尺寸分布：1400x788: 933, 1400x1050: 274, 1360x765: 167, 1916x1078: 151, 960x540: 49, 1920x1080: 36。UAVDT：1024x540: 38829, 960x540: 1906。
- “输入 Mpx”含 letterbox／画布填充；“内容 Mpx”只计图像内容（DensK1 的窗口内容取网格平均）；“局部缩放”= 最高分辨率那一路对图像内容的缩放系数（1.0 = 原生像素）。
- 以 1400×788（VisDrone 最常见尺寸）为例：UnifAll 6 窗（x∈{0, 512, 760}，y∈{0, 148}），SAHI640 6 片（x∈{0, 480, 760}，y∈{0, 148}）+ 1 次整图 → 两者都是 7 次前向、内容像素相同（2.688 Mpx）。UAVDT 1024×540：UnifAll 2 窗，SAHI640 2 片（640×540，填充到 640×544）+ 整图（640×352）。

## 4. 读法：分辨率效应 vs 协议效应

1. **同样的像素、不同的协议，结果差很远。** VisDrone 上 UnifAll 与 SAHI640 都是 7 次前向、内容像素相同（2.74 Mpx），small recall 却是 0.451 vs 0.218（SAHI640 甚至低于 F640）。差别只能来自协议本身（切片网格、sahi 的 GREEDYNMM/IOS 合并与默认推理参数），而不是像素数。UAVDT 上两者也是相同像素，0.782 vs 0.760。
2. **像素效率（边际 Δrecall / 增加 Mpx）：DensK1 最高。** VisDrone 0.295 / Mpx（F1280 0.132，UnifAll 0.085，SAHI640 −0.009）；UAVDT 0.144（SAHI640 0.101，UnifAll 0.091，F1280 0.069）。只多看一个最密的窗口，单位像素回报最大，但绝对 recall 不如 F1280／UnifAll。
3. **时延由前向次数决定，而不是像素数。** 每 Mpx 时延：F1280 单次前向最便宜（1660：VisDrone 20.6、UAVDT 20.2 ms/Mpx；5060 Ti：VisDrone 16.0 ms/Mpx），多次前向的 DensK1／UnifAll 约 38–49 ms/Mpx（两块 GPU 都是如此；SAHI640 为 135–184 ms/Mpx，另含 sahi 自身的切片/合并开销）。DensK1 只处理 F1280 一半的像素（0.82 vs 1.64 Mpx），在 1660 上时延却与 F1280 相当（34.06 vs 33.72 ms），在 5060 Ti 上反而更慢（40.26 vs 26.25 ms）——每次前向的固定开销（预处理、调用、同步、CPU 端合并）在这一模型规模上占主导。
4. **局部缩放可能解释跨集排序翻转（假设，未做因果检验）。** F1280 对图像的缩放：VisDrone 约 0.90（略低于原生），UAVDT 1024×540 为 1.25（放大）；窗口类协议恒为 1.0。VisDrone 上 UnifAll（1.0）> F1280（0.90），UAVDT 上 F1280（1.25）> UnifAll（1.0），与“小目标看到的有效尺度”一致。要验证需按目标尺度切片（见 Run K 的说明）。
5. 两块 GPU 的时延分列给出、从不合并；“快／慢”都只在同一 GPU 列内比较。

## 5. 对 C2（如何选协议）的含义

选协议应同时看两个预算：**像素预算**决定 recall 的上限（同一协议族内 recall 随像素与局部缩放上升），**前向次数**决定时延（在 YOLO11n 规模上，每次前向的固定开销大于像素成本）。因此：(i) 时延受限时，优先“单次前向 + 更大输入”（F1280），而不是“多次 640 前向”；(ii) 像素/显存受限时，DensK1 的单位像素回报最高；(iii) 不能用“处理像素多”替代协议选择——SAHI640 与 UnifAll 像素相同，recall 差 0.23（VisDrone）。所有时延结论都要带 GPU 名称（1660：F1280 与 DensK1 相当；5060 Ti：F1280 更快）。
